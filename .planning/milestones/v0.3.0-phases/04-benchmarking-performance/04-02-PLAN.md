<objective>
Refactor the FFI layer's repeated manual `libc::malloc`/`free` inference-allocation pattern (PERF-04).
Add an `FfiVec<T>` RAII wrapper (libc::malloc-backed, frees via libc::free on Drop) to `types.rs` and a
`macro_rules! alloc_inference_arrays!` to `lib.rs`, then apply the macro to the 13 byte-identical
5-array inference blocks (canonical instance lib.rs:188-254). Keep the C++-facing `anofox_free_*`
functions byte-identical — this is a Rust-side-only change with behavior unchanged.

Covers PERF-04 (RAII wrapper + codegen macro reducing per-call allocation overhead and leak risk,
with `test/sql` + `cargo test` staying green).

CRITICAL ABI CONSTRAINT (one-way door): the wrapper MUST allocate with `libc::malloc`, NEVER with
`Box`/`Vec`. The C++ `anofox_free_*` functions call C `free()`; on musl (WASM/CI targets) Rust's global
allocator and libc's malloc can differ, so `Box::into_raw`/`Vec::into_raw_parts` would silently break the
free contract. This allocator choice is a published-ABI decision gated below.

Purpose: reduce repetitive, error-prone manual allocation while preserving the exact C free contract, so
the code is safer and per-call overhead is lower without any behavior change.
Output: `FfiVec<T>` in types.rs, `alloc_inference_arrays!` in lib.rs, 13 refactored call sites, a
unit test asserting libc-freeability, all suites green.
</objective>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 1: DECISION — FfiVec allocator is libc::malloc (one-way ABI door)</name>
  <decision>Confirm FfiVec<T> allocates with libc::malloc and frees with libc::free, and MUST NOT use Box, Vec, or Rust's global allocator on any pointer crossing the FFI boundary.</decision>
  <context>
    This is a one-way door. The C++ side (anofox_free_result_inference, anofox_free_result_core, and all
    anofox_free_*) frees these pointers with C free() — the published FFI/ABI contract. Box/Vec would
    compile and appear to work on Linux/glibc (shared allocator) but silently corrupt on musl targets
    (WASM, some CI) where Rust's global allocator differs from libc malloc. Reversing this later means
    changing the published C++ free contract or re-auditing every call site. Per CONTEXT.md the C++ free
    functions must stay byte-identical, so libc::malloc is the only compatible allocator. This checkpoint
    exists because the choice is baked into the ABI before any code is written.
  </context>
  <options>
    <option id="libc-malloc">
      <name>libc::malloc-backed FfiVec (recommended)</name>
      <pros>Preserves the byte-identical C++ free() contract; works on glibc AND musl/WASM; the only choice consistent with the locked "no C++ changes" decision</pros>
      <cons>Requires explicit unsafe libc calls in the wrapper (mitigated by the RAII Drop + unit test)</cons>
    </option>
    <option id="rescope">
      <name>Reject / re-scope PERF-04</name>
      <pros>Avoids the unsafe allocation path entirely</pros>
      <cons>Cannot satisfy PERF-04 (RAII wrapper) without either a C++ free-contract change (excluded by CONTEXT.md) or leaving the manual malloc pattern as-is</cons>
    </option>
  </options>
  <reversibility rating="one-way">Allocator choice is baked into the published C++ free contract; changing it later breaks the ABI or forces a C++ change that CONTEXT.md excludes.</reversibility>
  <resume-signal>Select libc-malloc to proceed, or rescope to halt and revisit PERF-04 scope.</resume-signal>
